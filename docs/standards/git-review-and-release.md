# Git、评审与发布规范

## 分支

仓库只维护两个长期分支：

- `dev`：文档、开发和集成分支。
- `main`：经过负责人验收的稳定基线。

默认直接在 `dev` 完成当前授权范围内的工作，不创建额外长期分支。需要临时隔离时，
必须由项目负责人明确要求，完成后不得形成第三条长期发布线。

## 提交

- 提交范围必须单一、可解释，并保留用户已有变更。
- 提交信息使用简洁祈使句，文档变更可使用 `docs:` 前缀。
- 不提交 Token、环境文件、构建缓存或未审查的大型生成文件。
- 提交前检查 staged diff 并运行相关测试。

## 评审

每次评审至少确认：

- 变更属于当前授权阶段。
- 需求、ADR、技术设计和实现没有冲突。
- 租户、安全、数据口径、migration 和恢复影响已说明。
- 测试和 Gate 证据与实际运行一致。
- 文档链接、状态、ID 和追踪矩阵有效。

`dev` 合入 `main` 前必须由项目负责人验收。合并不能推导出生产部署或 Meta 写授权。

## CI

- `dev` 和 `main` 的 push/PR 必须运行文档检查。
- 实现阶段再按语言和组件增加类型检查、单元、集成、E2E 与安全测试。
- Required check 失败时不得将 `dev` 合入 `main`。

## 版本与变更日志

- 当前项目版本保持 `1.0.0`。
- 初始开发尚未开始期间，文档基线完善记录在 `1.0.0` 条目中。
- 后续版本策略必须在首次可运行发布前由项目负责人确定。
- 权限、接口、数据、ADR、Gate 或安全边界变化必须写入 `CHANGELOG.md`。

## 发布

- 代码合并、生产部署和 Meta 写授权是三个独立决定。
- production 发布必须满足阶段 Gate、部署授权、回滚、Secret、监控和 Runbook 前提。
- 不得从 `dev` 自动部署 production，除非后续以明确 ADR 和授权建立该流程。
