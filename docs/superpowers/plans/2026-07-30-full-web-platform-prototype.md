# Meta Ads 全流程 Web 平台原型执行计划

## 目标

制作一个可连续完成三个核心场景的响应式 Web 产品原型，并为每个场景准备独立 Codex
辅助流程。该原型验证产品结构、信息、状态和 Web/Codex 分工，不连接真实 Meta、不创建
Cloudflare 资源、不部署业务运行时，也不执行广告写操作。

## 固定产品形态

- Web 运营平台是业务产品主体。
- Codex 会话是前期 AI 生成、解释、诊断和建议入口。
- Web 前期不内置聊天助手。
- 不再制作或比较纯对话、纯 Web、Web 内置聊天三种壳层。
- 所有示例数据完全虚构，并持续显示“原型数据、无真实连接、无外部写入”。

## 原型范围

### 全局产品框架

建立统一、可点击的桌面优先框架：

- 工作区和广告账户切换。
- 数据时间、时区、归因和新鲜度。
- 当前角色和可用操作。
- 总览、素材中心、广告创建、广告管理、数据分析、测试与优化、设置与治理。
- 全局待办、审核失败、同步异常和安全告警。

移动端必须能打开和完成查看、审核与轻量修改，但复杂广告配置和素材编辑可以提示使用
桌面端。

### SC-01：素材到广告创建与发布状态

原型必须连续表现：

1. 搜索允许来源、上传或生成素材。
2. 查看来源、权利、规格、版本和变体。
3. 创建 Campaign、Ad Set 和 Ad。
4. 配置目标、受众、预算、排期、版位、素材和落地页。
5. 执行发布前检查并修复 `BLOCKER`。
6. 保存版本并进入人工确认。
7. 模拟待发布、发布中、已发布或审核失败状态，不调用真实 Meta。
8. 从审核失败返回对应素材或配置字段。

### SC-02：投放数据到诊断与行动

原型必须连续表现：

1. 在总览识别异常或待处理任务。
2. 进入数据分析并确认范围、时间、口径和新鲜度。
3. 下钻 Campaign、Ad Set、Ad 和素材。
4. 查看异常、证据、反证、置信度和缺失数据。
5. 形成诊断报告和待确认行动。
6. 清楚区分建议、待审批和已生效状态。

### SC-03：素材测试到持续优化

原型必须连续表现：

1. 从素材或广告对象选择变体。
2. 建立假设、主要变量、指标、数据条件和停止规则。
3. 显示测试状态、投放不均、追踪异常或配置变化。
4. 比较结果、置信度和干扰因素。
5. 保存 `KEEP`、`STOP`、`ITERATE` 或 `INCONCLUSIVE` 结论。
6. 将结论关联回素材和下一轮测试计划。

## Codex 辅助流程

Codex 不嵌入 Web 原型。每个场景单独提供一份可复现的上下文包：

| 场景 | 上下文与文档 | 候选 Skill | 结构化输出 |
| --- | --- | --- | --- |
| SC-01 | 商品、目标、受众、素材规则、广告字段说明 | `facebook-ads-creative`、`facebook-ads-campaign-builder` | 素材简报、广告配置和检查结果 |
| SC-02 | 脱敏指标、时间范围、口径和数据质量说明 | `facebook-ads-analysis`、`facebook-ads-optimization` | 诊断报告和待确认行动 |
| SC-03 | 变体、假设、测试条件和脱敏结果 | `facebook-ads-optimization` | 测试结论和下一轮计划 |

每份示例必须列出：

- 使用了哪些上下文、文档和 Skill。
- 哪些值是输入事实、哪些是推断、哪些仍未知。
- Codex 可以生成什么，以及不能读取、保存或执行什么。
- 如何把输出带入对应 Web 对象。

## 交互与内容要求

- 不能用孤立说明卡代替页面、对象、导航和状态变化。
- 核心操作必须有入口、反馈、错误、返回路径和下一步。
- 草稿、待确认、待审批、已发布、审核失败和数据不足状态必须可区分。
- 新手模式解释关键概念；高级模式展开详细字段和筛选。
- 素材、广告、数据、诊断和测试之间必须能相互导航。
- 原型不得保证审核通过、诊断正确或广告效果。

## 实施步骤

1. 建立产品信息架构、对象关系和页面清单。
2. 为三个场景定义共享虚构数据和状态机。
3. 实现全局框架、导航和跨模块对象链接。
4. 实现 SC-01 的素材、广告创建和审核失败闭环。
5. 实现 SC-02 的看板、下钻、诊断和行动闭环。
6. 实现 SC-03 的测试、结论和下一轮闭环。
7. 建立三份 Codex 上下文包和候选 Skill 契约。
8. 验证桌面完整流程与移动端查看、审核和轻量修改。
9. 运行内部链接、敏感信息、可访问性和原型确定性检查。
10. 由项目负责人完成一次完整产品走查并记录脱敏证据。

## DG0 验收

- 项目负责人能从全局导航识别完整产品范围。
- 三个场景均能在同一个 Web 产品中连续完成。
- 每个场景都能说明 Codex 使用的上下文、文档、Skill 和输出交接。
- 关键步骤覆盖率不低于 80%。
- 数据范围、权限、审批和 Meta 写操作关键误解为 0。
- 负责人确认产品不是聊天工具、精简控制台或个人定制产品。
- 所有结论明确限定为负责人低保真评审，不宣称真实用户、效率或广告效果验证。

任何一项核心条件未满足时，`DG0` 保持 `PARTIAL`，继续修改原型；不得启动 Phase 0。

## 明确禁止

- 真实 Meta、Cloudflare、客户或广告账户数据。
- Token、Cookie、Authorization Header 或生产响应。
- 运行时业务后端、真实 OAuth、真实发布或预算调整。
- 为了展示效果伪造实时同步、审核通过或广告优化结果。
- 将原型评审自动转换为部署或写操作授权。
