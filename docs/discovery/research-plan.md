# 产品定义确认计划

## 研究目标

通过结构化负责人决策，定义面向广泛 Meta 广告使用者的通用投放与数据分析助手，并用
代表性场景验证产品范围、流程、信息、异常和安全边界，为产品形态和 MVP 决策提供依据。

## 确认主体

- 项目负责人是本轮产品决策者，不作为被研究的个人用户样本。
- 当前不要求真实用户访谈，也不招募额外参与者。
- 产品目标是服务不同经验和职责的 Meta 广告使用者，具体覆盖范围仍需逐项确认。
- 负责人决策定义产品意图，但不能证明真实用户需求、可用性或市场适配。

Codex 只记录负责人主动提供的产品决定和完全脱敏的代表性场景，不访问日历、邮件、
聊天、会议系统、真实广告账户或客户数据。

## 确认顺序

1. 确认产品定位、支持用户类别、经验层级和非目标。
2. 确认广告创建、投放管理、数据分析、优化、报告和自动化的能力边界。
3. 建立至少 3 个代表性端到端场景，覆盖正常流程、异常和高风险操作。
4. 明确每个场景的输入、步骤、输出、失败处理、人工控制和验收条件。
5. 根据场景构造并比较对话式、Web 工作台和混合式三种低保真方案。
6. 将能力分为 `MVP`、`LATER`、`REJECTED`，形成产品定义。
7. 更新 `DQ-*`、产品定义和 `DG0`，由项目负责人最终确认。

## 决策质量

每项产品决定至少包含：

- 支持的用户或场景范围，以及明确非目标。
- 用户需要完成的任务和可观察结果。
- 必需输入、信息、控制、输出和异常处理。
- 人工确认、数据可信度、隐私和广告写操作边界。
- 可验证的 MVP 验收条件和延期项。

“适用于任何人”是通用产品目标，必须拆成明确的支持角色、经验层级和能力边界；在没有
真实用户证据时，文档必须标记为负责人定义，而不能表述为已验证事实。

## 证据与隐私

- 仓库只保存[证据登记](evidence-log.md)中的负责人决定和场景评审摘要。
- 原始录音、视频、逐字稿、姓名、邮箱、电话、聊天记录和客户数据不得入库。
- 每项研究推断必须区分 `FACT`、`INFERENCE`、`COUNTEREVIDENCE`。
- 证据冲突必须保留，不能通过删除反例制造共识。

## 停止与升级条件

出现以下情况时暂停综合并报告：

- 无法明确通用产品的支持用户、核心能力或首个 MVP 边界。
- 代表性场景不足 3 个，或无法形成可验证任务。
- 研究材料包含无法安全脱敏的客户或个人数据。
- 负责人决策互相冲突且无法确定权威优先级。
- 需要接触外部用户、真实 Meta 账户或其他未授权资源。
